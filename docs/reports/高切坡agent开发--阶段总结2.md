# 高切坡 Agent 开发 -- 阶段总结二

## 项目阶段性总结

本阶段对高切坡系统智能查询 Agent 进行了重新收敛和重构，开发重心从“基于数据库设计文档理解业务”调整为“基于真实数据库导出的 schema 构建业务查询能力”。

阶段一中，系统主要依赖《高切坡数据库设计文档》中的表结构说明来理解业务。但在实际验证过程中发现，设计文档中的表和字段与真实数据库存在明显差异，部分文档表在数据库中不存在，部分真实表也没有在文档中完整体现。因此，本阶段将设计文档降级为历史参考材料，核心依据改为真实数据库结构、真实字段、真实样例值和真实查询结果。

当前系统已经从一个基础 Text-to-SQL 原型，进一步收敛为一个面向高切坡业务的智能查询 Agent：用户可以用自然语言提问，系统结合真实 schema 业务解释自动选择相关表、生成 SQL、执行达梦数据库查询，并将结果拆分为生成 SQL、查询结果表格、查询总结和 Agent 日志。

## 一、阶段目标

本阶段主要目标包括：

1. 解决数据库设计文档与真实数据库不一致导致的查询失败问题。
2. 从真实达梦数据库导出完整 schema，并生成结构化 JSON。
3. 对真实 schema 进行初版中文业务解释，包括字段别名、枚举含义、关联关系和查询提示。
4. 将 schema 解释接入 Agent，使 Agent 查询时优先参考真实数据库结构。
5. 优化前端交互，将生成 SQL、查询结果表格、查询总结、Agent 日志分区展示。
6. 增加类似 DeepSeek 的查询过程展示能力，让用户在等待结果时看到 Agent 正在做什么。
7. 修复查询结果只出现在 Agent 日志或 Final Answer 中、表格组件不展示真实数据的问题。
8. 建立项目文档目录，沉淀阶段总结、流程图和业务逻辑图。

## 二、关键调整

### 1. 从设计文档驱动调整为真实数据库驱动

阶段一中，系统使用数据库设计文档作为主要 schema 来源。但实际运行中出现过类似问题：

```text
include_tables {'geo_wyjcsjjlb', 'qcqfhgxcjl'} not found in database
```

这说明文档中的部分表并不存在于当前真实数据库中。如果继续依赖设计文档，Agent 会不断生成针对不存在表的 SQL，导致查询失败。

本阶段重新确定 schema 建设原则：

- 真实数据库中存在的表，才作为 Agent 查询候选表。
- 真实数据库中存在的字段，才作为 SQL 生成依据。
- 设计文档只作为辅助参考，不再作为物理结构事实来源。
- 对真实字段进行业务解释，提升自然语言到 SQL 的语义映射能力。

### 2. 真实 schema 导出与对比

本阶段新增了 schema 导出与分析脚本，用于从真实数据库读取表结构，并与设计文档中的表结构进行对比。

当前已生成的核心 schema 文件包括：

```text
backend/schema_exports/database_schema.json
backend/schema_exports/document_schema.json
backend/schema_exports/schema_comparison.json
backend/schema_exports/database_schema_explained.json
backend/schema_exports/schema_chunks.jsonl
backend/schema_exports/table_profile.json
backend/schema_exports/core_table_candidates.json
backend/schema_exports/business_starter_pack.json
```

其中：

- `database_schema.json`：真实数据库导出的表和字段结构。
- `document_schema.json`：从 Word 设计文档中提取出的表结构。
- `schema_comparison.json`：真实数据库与设计文档的差异对比。
- `database_schema_explained.json`：在真实 schema 基础上生成的中文业务解释。
- `schema_chunks.jsonl`：适合后续接入向量数据库的 schema chunk。
- `table_profile.json`：真实表的数据画像，包括样例值、时间字段、状态字段、枚举字段等。
- `core_table_candidates.json`：根据表名、字段和数据情况推断出的核心业务表候选。
- `business_starter_pack.json`：用于 Agent 业务理解的初版知识包。

### 3. schema 业务解释初版

由于开发者并非原数据库设计人员，且数据库表数量较多，本阶段没有试图一次性人工梳理所有业务关系，而是先采用“真实结构 + 自动画像 + 初版解释”的方式建立可迭代 schema 知识。

当前 schema 解释重点包含：

- 表中文业务含义。
- 字段中文别名。
- 常见字段用途，例如编号、时间、状态、位置、人员、影像、预警等。
- 枚举字段可能含义。
- 表之间可能的关联字段。
- 常用查询提示。
- 高频业务问题对应的候选表。

该方式不是最终知识库，但已经能显著降低 Agent 选错表、用错字段的概率。

## 三、Agent 查询链路

【占位符：高切坡 Agent 查询流程图】

建议放置图片：

```text
docs/diagrams/高切坡Agent查询流程图.png
```

当前查询链路如下：

1. 用户在前端输入自然语言问题。
2. 前端通过 `/api/query/stream` 发起流式请求。
3. 后端接收问题后，基于问题选择候选表。
4. 后端加载真实数据库 schema 业务解释，构造 Agent Prompt。
5. LangChain SQL Agent 根据问题调用工具：
   - `sql_db_list_tables`
   - `sql_db_schema`
   - `sql_db_query_checker`
   - `sql_db_query`
6. 后端通过回调机制实时捕获 Agent 过程，并推送给前端。
7. Agent 生成 SQL 并执行数据库查询。
8. 后端记录最后一次成功执行的 SQL。
9. 后端使用该 SQL 重新查询数据库，生成表格数据。
10. 前端展示生成 SQL、查询结果表格、查询总结和 Agent 日志。

本阶段明确了一个重要原则：

```text
Final Answer 只作为查询总结，不作为查询结果表格的数据来源。
查询结果表格必须来自真实 SQL 查询返回的 columns 和 rows。
```

## 五、前端交互优化

阶段一的页面较为粗糙，且查询结果、SQL、日志和总结之间边界不清。本阶段对前端展示结构进行了调整。

当前页面主要分为四个结果区域：

1. 生成 SQL

用于展示 Agent 当前生成或最终使用的 SQL，方便开发人员和业务人员核查查询逻辑。

2. 查询结果

用于展示真实数据库查询返回的表格数据。该区域直接消费后端返回的 `columns` 和 `rows`，不再从 Agent 文本总结中解析数据。

3. 查询总结

用于展示 Agent 的 Final Answer，即对查询结果的自然语言解释。

4. Agent 日志 / 思考过程

用于展示 Agent 的工具调用过程、SQL 校验过程、查询执行过程和最终日志。查询过程中默认展开，查询完成后可折叠。

当前流式事件包括：

```text
progress：展示 Agent 当前步骤
sql：展示生成或执行的 SQL
summary：展示查询总结
final：展示最终结构化结果
error：展示错误信息
```

## 六、已解决问题

### 1. 设计文档中的表不存在

原问题：

```text
include_tables {'geo_wyjcsjjlb', 'qcqfhgxcjl'} not found in database
```

处理方式：

- 导出真实数据库 schema。
- 以真实数据库表作为 Agent 查询边界。
- 动态选择真实存在的候选表。
- 将文档表结构仅作为对比和参考。

### 2. Agent 日志中出现 CREATE TABLE

用户在日志中看到 `CREATE TABLE`，容易误以为系统执行了建表语句。

实际原因：

- LangChain SQL 工具在查看表结构时，会以 DDL 形式展示表结构。
- 这是用于帮助模型理解 schema，不是实际执行建表。

处理方式：

- 在日志清洗中隐藏完整 DDL 细节。
- 将其替换为“表结构详情已隐藏，仅用于 Agent 理解字段，不是执行建表语句”。

### 3. 查询结果没有显示在表格中

原问题：

- 数据库实际上查到了数据。
- Agent 日志中能看到查询结果。
- 但前端查询结果组件显示为空。

原因：

- 前端表格依赖后端返回的 `columns` 和 `rows`。
- 后端此前主要从日志中猜测 SQL，再重新查询生成表格。
- 如果日志解析不稳定，或者只拿到 Final Answer，就会导致表格为空。

处理方式：

- 后端在 Agent 调用 `sql_db_query` 时直接记录真实执行的 SQL。
- 工具返回成功后，将该 SQL 标记为 `last_success_query_sql`。
- 最终返回时优先使用最后一次成功执行的 SQL 重新查询数据库。
- 查询总结仍然使用 Agent Final Answer。

### 4. 用户等待时间过长

原问题：

- 用户点击查询后，需要等待较久才能看到最终结果。
- 页面缺少中间过程反馈。

处理方式：

- 后端改为 SSE 流式响应。
- 前端实时展示 Agent 思考过程和工具调用过程。
- 查询完成后自动折叠过程面板。
- 用户可以重新展开查看完整日志。

### 5. 多端访问与白屏问题

本阶段排查过 `localhost:5173`、`10.61.48.10:5173`、`8000` 等访问方式的差异。

最终结论：

- 手机无法访问一度与局域网连接状态有关。
- 电脑访问 `localhost:5173` 卡住，与本地访问路径和静态资源服务方式有关。
- 通过局域网 IP 访问可以正常进入。

该问题已作为开发过程经验保留，后续生产化部署时应统一前后端访问地址、静态资源路径和反向代理策略。

## 八、当前阶段结论

本阶段完成了高切坡智能查询 Agent 的一次关键收敛：

- 查询依据从设计文档切换到真实数据库。
- schema 从原始结构升级为带业务解释的 JSON 知识。
- Agent 从单纯生成 SQL，升级为结合 schema 知识选择表和字段。
- 前端从简单输入输出页面，升级为可展示 SQL、表格、总结和思考过程的查询界面。
- 查询结果与查询总结完成解耦，避免把 Final Answer 当作真实表格数据。

当前系统已经具备较清晰的最小可用形态：

```text
自然语言问题
-> schema 业务知识增强
-> SQL Agent 生成并执行查询
-> 表格展示真实结果
-> 自然语言总结解释结果
-> Agent 日志支撑可追溯调试
```

## 九、当前已知限制

1. schema 业务解释仍是初版

当前解释主要基于字段名、样例值、表名和启发式规则生成，仍需要结合真实业务人员反馈继续修正。

2. 枚举含义仍存在不确定性

部分状态字段、异常字段、审核字段的枚举值含义尚未完全确认。例如 `0/1/2` 在不同表中可能代表不同业务状态。

3. 表关系仍需要验证

当前关联关系主要根据字段名和业务推断得到，例如 `gqpbh`、`hcs_id`、`jc_id` 等，需要通过真实查询和业务规则继续验证。

4. 复杂多表查询仍可能不稳定

对于跨预警、监测、巡查、基础档案的复杂查询，Agent 仍可能出现选表不准、关联条件不完整、字段含义误判等问题。

5. 缺少标准化测试集

目前主要依赖人工提问验证。后续需要建立高频问题集、期望 SQL、期望结果类型和失败分类。

6. 缺少业务结果解释规范

当前总结仍由 Agent 自由生成，后续可以按业务场景制定固定总结模板，例如异常列表、风险等级、时间范围、处置建议等。

## 十、下一阶段建议

### 1. 建设高频业务问题测试集

整理 50 到 100 条高切坡常见业务问题，覆盖：

- 基础信息查询。
- 异常状态查询。
- 裂缝落石查询。
- 预警专报查询。
- 专业监测查询。
- 巡查记录查询。
- 人员责任查询。
- 时间范围查询。
- 单坡详情追问。
- 多表关联查询。

每条问题应记录：

- 用户自然语言问题。
- 期望业务意图。
- 期望查询表。
- 期望关键字段。
- 期望 SQL 特征。
- 是否需要表格结果。
- 是否需要业务总结。

### 2. 继续完善 schema 解释

优先完善核心业务表，而不是平均处理所有表。

建议优先级：

1. 高切坡基础信息表。
2. 群测群防 / 巡查 / 监测记录表。
3. 预警报告和预警内容表。
4. 专业监测表。
5. 灾险情或隐患上报表。
6. 人员责任表。
7. 影像和模型资料表。

### 3. 建设轻量 Schema RAG

将 `schema_chunks.jsonl` 接入向量数据库，使 Agent 在查询前先检索相关表和字段说明。

推荐 chunk 粒度：

```text
一个表一个 chunk。
每个 chunk 包含表说明、字段别名、枚举含义、关联关系、查询提示和典型问法。
```

### 4. 增加 SQL 执行失败分级

当前 SQL 失败主要依赖 Agent 自动修正。后续可以增加更明确的失败分类：

- 表不存在。
- 字段不存在。
- 字段类型错误。
- 枚举值错误。
- 方言语法错误。
- 关联条件错误。
- 查询无结果。

不同失败类型给出不同修复策略。

### 5. 优化查询结果的业务展示

当前结果表格仍直接展示数据库字段名。后续可以基于字段别名做展示优化：

- `gqpbh` 显示为“高切坡编号”。
- `createdOn` 显示为“创建时间 / 监测时间”。
- `isCrack` 显示为“是否存在裂缝”。
- `locX`、`locY` 显示为“经度 / 纬度”。

同时可以增加枚举值翻译，例如：

```text
1 -> 是 / 存在 / 异常
0 -> 否 / 不存在 / 正常
```

但该映射必须基于具体字段确认，不能全局简单套用。

### 6. 形成演示版闭环

下一阶段可以围绕演示场景打磨：

- 准备 10 条稳定可查询的问题。
- 每条问题能展示 SQL、表格、总结和日志。
- 对查询失败场景给出友好提示。
- 准备流程图、业务逻辑图、阶段总结材料。
- 固化启动命令和访问地址。

## 十一、阶段二总结

阶段二的核心价值不是新增了多少页面或脚本，而是明确了系统的正确方向：

```text
高切坡智能查询 Agent 必须建立在真实数据库结构之上。
设计文档可以参考，但不能替代真实 schema。
查询结果必须来自真实 SQL 返回值。
Agent Final Answer 应当作为业务总结，而不是表格数据来源。
```

在这个基础上，系统已经具备继续迭代的条件。后续工作的重点应从“能不能跑通”转向“能不能稳定回答高频业务问题”，逐步沉淀 schema 知识、业务规则、测试集和演示闭环。

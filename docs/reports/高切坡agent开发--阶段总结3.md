# 高切坡 Agent 开发 -- 阶段总结三

## 项目阶段性总结

本阶段开发重点从“网页端智能查询能力”进一步延伸到“移动端可用性与语音交互能力”。如果说阶段二主要解决的是“查得准、看得清、过程可解释”，那么本阶段主要解决的是“在手机上能不能真正用起来，以及语音链路能不能真正跑通”。

经过这一阶段的调整，系统已经完成了从单一网页原型向“网页 + Android App”双端可用形态的推进，并初步打通了语音输入、语音转写、查询结果播报等交互链路。

当前系统可以概括为：

```text
用户既可以在电脑浏览器中通过自然语言查询高切坡业务数据，也可以在 Android App 中通过语音输入发起查询，并获得表格结果、查询总结、Agent 思考过程和结果播报。
```

## 一、本阶段目标

本阶段主要目标包括：

1. 将现有高切坡智能查询页面迁移为可运行的 Android App 形态。
2. 解决 App 中前端页面、后端接口、局域网访问、跨域和流式请求之间的兼容问题。
3. 为移动端增加语音输入能力，并摆脱对浏览器原生语音识别兼容性的强依赖。
4. 为移动端增加查询结果播报能力，并补齐开始、暂停、继续、停止等基本控制能力。
5. 统一梳理浏览器端与 App 端在语音输入、语音播报方面的能力边界，形成可汇报、可演示、可继续迭代的阶段成果。

## 二、本阶段核心成果

### 1. 完成 Android App MVP 形态

本阶段已基于前端现有 Vue 页面接入 Capacitor，生成 Android 原生工程，并完成手机真机安装与运行验证。

当前移动端整体架构为：

```text
前端页面：Vue + Vite
移动端容器：Capacitor Android
后端接口：FastAPI
数据库：达梦数据库
```

这意味着系统不再局限于浏览器访问，而是已经具备了一个可安装、可在手机上直接运行的查询 App 雏形。

### 2. 打通 Android App 查询链路

网页端最初依赖浏览器 `fetch + SSE` 展示流式思考过程，但在 Android WebView 场景下，这条链路稳定性不足，容易出现：

- `Failed to fetch`
- 跨域限制
- 流式事件兼容性不稳定

因此，本阶段针对 Android App 做了查询链路调整：

- 浏览器网页端：继续保留 `/api/query/stream` 的流式查询方式。
- Android App 端：改用原生 HTTP 请求 `/api/query`，优先保证查询能力稳定可用。

这样做的核心取舍是：

```text
移动端先保证“查得通”，再考虑“流式体验是否完全复刻”。
```

该调整后，Android App 已能够稳定返回：

- 查询结果表格
- 查询总结
- SQL
- Agent 日志

### 3. 打通 App 端“录音上传 + 后端转写”语音输入链路

本阶段一个关键转向，是放弃对浏览器原生语音识别或系统语音识别服务的过度依赖，改为：

```text
App 原生录音 -> 上传后端 -> 后端转文字 -> 写回输入框
```

原先尝试过两类方式：

1. 浏览器 `SpeechRecognition / webkitSpeechRecognition`
2. Android 系统原生语音识别插件

实际验证发现，这两条路线都存在明显问题：

- 浏览器兼容性差
- 手机不同浏览器差异大
- 部分设备缺少系统语音识别服务
- 移动端录音权限和安全策略影响较大

因此，本阶段最终收敛为更稳妥的方案：

- App 端只负责原生录音
- 后端统一负责语音转写
- 识别文本自动回填输入框

这条链路已经打通，并完成了实际设备验证。

### 4. 后端语音转写切换为本地 ASR

本阶段语音转写最开始尝试使用 OpenAI 兼容音频接口，但在实际测试中发现：

- 当前查询模型所使用的兼容网关并不一定支持音频转写接口
- 即使接口风格兼容 OpenAI，也不代表支持 `audio/transcriptions`
- 第三方服务的模型名称、接口能力和错误形式不稳定

因此，本阶段进一步将 ASR 方案调整为：

```text
服务器本地 faster-whisper 模型转写
```

这样带来的好处包括：

- 不再依赖第三方 ASR API
- 不再需要额外音频转写密钥
- 中文录音转写链路掌握在本地服务端
- 后续浏览器端也可以复用同一套后端 ASR 接口

当前后端 ASR 已具备：

- base64 音频上传接收
- 音频解码与容错处理
- 本地模型加载与缓存
- 中文语音转写返回

## 三、语音播报能力演进

### 1. 浏览器端播报

当前电脑浏览器中的结果播报仍采用浏览器原生 `speechSynthesis`。

这一方案在桌面 Chrome / Edge 下基本可用，优点是接入简单、无需额外服务。

同时，本阶段也对浏览器端播报做了细化修复：

- 修复点击“停止”后被误判为播报失败的问题
- 对浏览器取消播报和中断播报做了错误分流
- 将页面提示语优化得更准确

### 2. Android App 端播报

移动端原生播报在本阶段经历了多轮尝试。

早期路线主要依赖系统 TTS 插件，但在暂停、继续等控制能力上不稳定，实际体验不理想。后续改为：

```text
原生文本转音频 + MediaPlayer 控制播放
```

这样 App 端播报能力不再依赖浏览器 `speechSynthesis`，而是走原生音频播放逻辑，具备：

- 开始播报
- 暂停
- 继续
- 停止

这一点对移动端演示非常关键，因为它使得播报交互不再完全受限于手机浏览器本身的语音能力。

## 四、浏览器端语音输入能力调整

在网页端，本阶段也对语音输入做了收敛：

- 浏览器优先走 `MediaRecorder` 录音
- 录音结束后上传后端 `/api/asr`
- 由本地 ASR 返回转写文本

只有在浏览器录音能力不可用时，才退回到老的浏览器语音识别判断逻辑。

这一调整的意义在于：

```text
网页端语音输入开始逐步与 App 端共用同一套后端转写能力。
```

这样可以减少“某些浏览器能识别、某些浏览器不能识别”的不确定性。

不过，本阶段也明确验证出一个现实边界：

- 手机浏览器中的麦克风录音通常要求 HTTPS 或 localhost
- 部分国产浏览器即便在安全上下文中，也可能对语音相关能力支持较差

因此，当前结论是：

- 电脑浏览器：语音输入与播报可用
- 手机浏览器：语音输入在 HTTPS 条件下可用，但播报依赖浏览器能力
- Android App：语音输入与播报链路更稳，更适合作为移动端演示和后续主形态

## 五、本阶段解决的关键问题

### 1. Android App 中请求失败

原问题：

- App 页面能打开
- 但查询时出现 `Failed to fetch`

处理方式：

- 为 App 查询链路单独切换到原生 HTTP
- 避免继续依赖 WebView 中不稳定的流式 fetch
- 后端补充更明确的跨域放行策略

结果：

- App 查询链路已打通

### 2. 系统语音识别插件兼容性差

原问题：

- 点击中文语音输入后提示当前设备不支持原生语音识别

原因：

- 该插件本质仍依赖手机系统自带语音识别服务
- 部分设备并不具备可用服务

处理方式：

- 放弃系统语音识别插件路线
- 改为原生录音 + 后端本地 ASR

结果：

- 语音输入能力不再依赖系统是否自带识别服务

### 3. 音频 base64 解码失败

原问题：

- Android 录音上传后出现“录音数据格式无效，无法解码”

原因：

- 插件输出的 base64 带有换行、前缀等格式差异

处理方式：

- 后端增强 base64 音频解码容错
- 兼容换行、空格、Data URL 前缀和缺失 padding

结果：

- 录音上传转写链路恢复正常

### 4. 外部 ASR API 不稳定或不兼容

原问题：

- 使用兼容 OpenAI 的音频转写接口时返回 400
- 查询模型可用，但语音转写接口不可用

处理方式：

- 停止依赖第三方兼容网关做 ASR
- 切换为本地 faster-whisper

结果：

- 本地 ASR 跑通
- 减少外部服务不确定性

### 5. 浏览器停止播报误报错误

原问题：

- 在电脑端点击“停止”后，页面提示“语音播报失败”

原因：

- 浏览器原生取消播报被统一走到错误处理逻辑

处理方式：

- 区分用户主动取消与真实播报失败

结果：

- 停止播报时不再误报

## 六、当前系统形态

经过本阶段调整，当前系统可以分为三种使用场景：

### 1. 电脑浏览器

可用能力：

- 自然语言查询
- 查询过程展示
- SQL 展示
- 表格结果展示
- 查询总结
- Agent 日志
- 浏览器录音上传转写
- 浏览器语音播报

### 2. 手机浏览器

可用能力：

- 页面查询
- 查询结果展示
- 在 HTTPS 条件下尝试浏览器录音上传转写

当前边界：

- 国产浏览器播报能力不稳定
- 部分浏览器不支持 `speechSynthesis`

### 3. Android App

可用能力：

- 页面查询
- 原生 HTTP 查询
- 原生录音上传转写
- 原生播报

当前定位：

```text
Android App 已经具备可演示、可继续迭代的 MVP 形态。
```

## 七、当前能力边界与判断

本阶段一个很重要的收获，不是单纯“把功能做出来”，而是把不同终端的能力边界摸清楚了。

当前可以明确的判断是：

1. 浏览器原生语音能力并不可靠

- 语音识别兼容性差
- 语音播报在手机浏览器上差异大

2. 对移动端来说，App 方案比手机浏览器方案更稳

- App 可使用原生录音
- App 可使用原生播放
- App 查询链路更可控

3. 本地 ASR 是一条正确方向

- 可控
- 不依赖外部兼容服务
- 有利于后续统一网页端与 App 端语音输入

## 八、下一阶段建议

下一阶段建议重点不再是“继续证明功能能不能跑通”，而是围绕稳定性、统一性和演示完整性继续收敛：

1. 继续打磨 Android App 体验

- 优化播报控制体验
- 优化移动端页面布局
- 补齐异常提示与状态提示

2. 继续收敛浏览器端语音能力边界

- 对不支持语音播报的浏览器给出更明确提示
- 引导用户优先使用支持的浏览器或 Android App

3. 评估统一后端 TTS 的可行性

- 若后续要实现浏览器和手机浏览器统一播报
- 可考虑新增后端 TTS 音频合成接口
- 前端统一使用音频播放器，而不再依赖 `speechSynthesis`

4. 继续完善高频业务问题模板

- 将移动端体验和查询口径稳定性一起纳入测试
- 形成更完整的演示问题集和回归测试集

## 九、阶段总结

本阶段的核心价值，不只是“做了语音输入和语音播报”，而是把系统从桌面网页原型进一步推进成了一个真正可移动演示、可手机操作、可语音交互的高切坡智能查询工具。

相比阶段二，本阶段最重要的增量在于：

```text
完成了 Android App MVP；
完成了本地 ASR 语音输入链路；
完成了移动端查询能力打通；
明确了浏览器与 App 在语音能力上的边界。
```

也就是说，当前系统已经不仅仅是“一个能查 SQL 的网页”，而是开始具备“多端可用的智能查询应用”雏形。

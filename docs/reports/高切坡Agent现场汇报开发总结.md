# 高切坡系统智能查询 Agent 现场汇报开发总结

## 一、项目定位

本项目当前已经从一个基础的 Text-to-SQL 原型，收敛为面向高切坡业务场景的智能查询 Agent。

系统目标是让业务人员不需要了解数据库表名、字段名和 SQL 写法，也可以用自然语言查询高切坡相关数据。系统负责理解用户问题，自动匹配真实数据库表和字段，生成查询 SQL，执行达梦数据库查询，并将结果以表格、总结、日志和语音播报的方式展示出来。

一句话概括：

```text
用户说业务语言，系统转换成数据库语言，并把真实查询结果解释给用户。
```

## 二、当前完成情况

### 1. 已实现自然语言查询

用户可以直接输入类似问题：

- 我想知道最近有哪些高切坡存在异常状态。
- 哪些高切坡最近出现裂缝或落石？
- 最近有哪些预警信息？
- 查询某个高切坡的基本信息。
- 哪些高切坡处于异常状态，并告诉我属于哪一种异常类型。

系统会自动完成：

- 理解用户意图。
- 选择候选业务表。
- 生成 SQL。
- 查询达梦数据库。
- 返回表格结果。
- 生成业务总结。

### 2. 已接入真实数据库 schema

前期尝试过依赖数据库设计文档，但实际验证发现，设计文档中的部分表和字段与真实数据库不一致。

本阶段已经调整为以真实数据库为准：

- 从真实达梦数据库导出表结构。
- 生成真实 schema JSON。
- 对真实表和字段补充中文业务解释。
- 建立字段别名、枚举含义、关联关系和查询提示。
- 将这些 schema 知识接入 Agent。

这样可以避免 Agent 查询不存在的表或使用错误字段。

### 3. 已形成结构化展示页面

当前前端页面分为几个核心区域：

- 用户问题输入区。
- Agent 思考过程。
- 生成 SQL。
- 查询结果表格。
- 查询总结。
- Agent 日志。
- 结果语音播报。

其中，“查询结果表格”和“查询总结”已经分离：

```text
查询结果表格：来自数据库真实 SQL 查询结果。
查询总结：基于查询结果表格，由 LLM 进行业务分析后生成。
```

这解决了之前“结果只在 Agent 日志里，表格不显示”以及“Final Answer 不能代表真实结果表”的问题。

### 4. 已支持实时过程展示

用户提交问题后，不再是长时间空等。

系统会实时显示：

- 正在连接数据库。
- 正在检索 schema 知识。
- 正在初始化 Agent。
- 正在生成 SQL。
- 正在执行查询。
- 正在整理表格。
- 正在基于结果生成业务分析。

查询完成后，思考过程可以折叠，保留完整日志用于排查。

### 5. 已支持查询结果语音播报

当前已经新增结果播报功能：

- 开始播报。
- 暂停。
- 继续。
- 停止。

播报内容包括：

- 查询总结。
- 查询结果总条数。
- 表格前几条关键记录。

这个功能适合现场演示，也便于非技术人员快速了解结果。

### 6. 已支持中文语音输入

页面已经加入中文语音输入按钮。

用户可以通过语音说出问题，系统自动写入输入框，再发起查询。

由于浏览器安全限制，语音输入通常需要 HTTPS 或 localhost 环境。本项目已经新增 HTTPS 开发服务，支持局域网内通过 HTTPS 地址访问。

## 三、关键业务逻辑调整

### 1. 查询结果与查询总结解耦

当前系统不再把 Agent 的 Final Answer 直接当成查询结果。

现在的处理逻辑是：

```text
Agent 生成 SQL
-> 数据库执行 SQL
-> 后端拿到 columns 和 rows
-> 前端展示真实表格
-> 后端再把真实结果表交给 LLM 做分析
-> 查询总结展示分析结果
```

这样可以保证：

- 表格是真实数据库结果。
- 总结是基于真实表格分析。
- 避免 LLM 在没有结果依据的情况下自由发挥。

### 2. 针对高频关键问题加入稳定业务模板

对于“异常状态”和“异常类型”这类关键问题，不能完全依赖 LLM 自由选择字段。

例如用户问：

```text
我想知道哪些高切坡处于异常状态，并告诉我属于哪一种异常类型。
```

系统现在会优先走稳定业务查询模板，直接按照具体异常项识别异常类型，包括：

- 裂缝。
- 坡面裂痕。
- 落石。
- 坡面破坏。
- 道路或挡墙开裂。
- 排水沟堵塞。
- 排水口堵塞。
- 监测设施异常。
- 坡周乱搭乱堆。
- 坡面鼓胀或反翘。

同时明确：

```text
overallSituation 只能表示总体异常，不能单独作为异常类型。
```

这样避免出现“状态良好但被总结为异常类型”的错误理解。

### 3. 同一句问题保持稳定查询口径

之前同一个问题多次查询，可能由于大模型生成 SQL 的细微差异，导致结果口径不一致。

当前已经加入 SQL 稳定缓存：

- 第一次成功查询后，保存“问题 -> SQL”的映射。
- 后续相同问题优先复用已验证 SQL。
- 缓存的是 SQL，不缓存结果。
- 数据库数据变化后，仍会执行同一条 SQL 获取最新结果。

这保证了：

```text
同一句问题，查询口径稳定；数据结果，仍然来自实时数据库。
```

## 四、当前系统能力边界

当前系统已经具备可演示、可验证的最小可用能力，但仍属于迭代版本。

### 已具备能力

- 自然语言查询高切坡业务数据。
- 自动生成 SQL。
- 查询真实达梦数据库。
- 表格化展示结果。
- 基于真实结果生成查询总结。
- 展示 Agent 思考过程。
- 展示完整 Agent 日志。
- 支持中文语音输入。
- 支持查询结果语音播报。
- 支持 HTTPS 局域网访问。
- 支持高频问题测试集。
- 支持真实 schema 解释文件。

### 当前限制

1. schema 业务解释仍是初版

虽然已经基于真实数据库生成了中文解释，但部分字段含义、枚举值和表关系仍需要业务人员继续校准。

2. 复杂跨表查询仍需要继续打磨

涉及基础信息、巡查、专业监测、预警、复核、影像资料等多表综合分析时，仍可能需要增加稳定模板或业务规则。

3. 语音能力依赖浏览器

中文语音输入和播报依赖浏览器能力。Chrome / Edge 支持较好，不同手机浏览器支持情况可能不同。

4. 当前还不是生产部署形态

目前是开发环境演示版，后续生产化需要统一部署方式、HTTPS 证书、权限控制、日志留存和异常监控。

## 五、推荐现场演示流程

### 演示 1：基础自然语言查询

输入：

```text
我想知道最近有哪些高切坡存在异常状态
```

讲解重点：

- 用户不需要知道表名字段名。
- 系统自动理解“异常状态”。
- 页面实时展示思考过程。
- 最终展示 SQL、表格和总结。

### 演示 2：异常类型查询

输入：

```text
我想知道哪些高切坡处于异常状态，并告诉我属于哪一种异常类型
```

讲解重点：

- 系统不是简单返回“异常/正常”。
- 会识别具体异常类型。
- 结果表里会出现 `abnormal_type`。
- 总结基于真实结果表生成。

### 演示 3：裂缝或落石查询

输入：

```text
哪些高切坡最近出现裂缝或落石？
```

讲解重点：

- 系统能理解地灾业务词汇。
- 裂缝、落石会映射到真实数据库字段。
- 返回结果包含编号、时间、异常项等信息。

### 演示 4：语音输入

点击“中文语音输入”，说：

```text
查询最近有异常的高切坡
```

讲解重点：

- 支持非键盘输入。
- 适合移动端或现场快速查询。
- 需要 HTTPS 和麦克风权限。

### 演示 5：结果播报

查询完成后点击：

```text
开始播报
```

讲解重点：

- 系统可以把查询总结和前几条结果读出来。
- 支持暂停、继续、停止。
- 便于现场汇报和非技术人员查看。

## 八、下一步建议

### 1. 建立标准测试集

基于当前 150 条语义识别测试问题，挑选 30 到 50 条作为核心回归测试集。

每条测试问题记录：

- 问题。
- 期望表。
- 期望字段。
- 期望 SQL 特征。
- 期望结果类型。
- 是否命中稳定模板。

### 2. 继续补充稳定业务模板

建议优先补充：

- 最近异常高切坡。
- 最近裂缝落石。
- 预警专报查询。
- 某个高切坡详情。
- 某个高切坡最近巡查、监测、预警综合情况。
- 按区县统计高切坡数量和异常数量。

### 3. 业务人员校准字段含义

需要业务人员重点确认：

- 状态字段含义。
- 枚举值含义。
- 异常字段含义。
- 表之间的关联关系。
- 哪些字段可以代表“风险”“异常”“预警”“处置”。

### 4. 推进生产化部署

如果进入正式使用，需要进一步补齐：

- 正式 HTTPS 证书。
- 访问权限控制。
- 查询日志审计。
- 错误监控。
- 用户操作记录。
- 敏感字段屏蔽。
- 服务稳定性部署。

## 九、阶段结论

当前系统已经完成从“能生成 SQL 的原型”到“能面向高切坡业务进行自然语言查询”的关键转变。

最重要的改进是：

```text
系统以真实数据库为准，
以真实查询结果为准，
以业务解释增强 Agent，
以结果表驱动查询总结。
```

目前已经具备面向甲方进行阶段演示的能力，并且后续可以沿着“核心业务问题稳定模板 + schema 知识增强 + 标准测试集”的路线继续迭代。
